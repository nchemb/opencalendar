# BookKit Audit v1

**Date:** 2026-09-22
**Scope:** every file under `lib/`, `app/`, `components/`, `prisma/`, `public/widget.js`, `tests/`, plus `README.md`, `CHANGELOG.md`, `docker-compose.yml`, `.env.example`, `next.config.js`, `vercel.json`, `.github/workflows/ci.yml`, `scripts/`.
**Method:** every file in scope was read in full (not grep-sampled) directly by the auditor, cross-checked against the test suite and CI config. Five parallel sub-agents were also dispatched to independently review the same modules; they did not return results within this session's time budget, so this report reflects the auditor's own direct, line-by-line review of 100% of the requested scope. No source files were modified.

## TL;DR

This codebase is **not** what "built a few model generations ago, don't trust it" usually means in practice. The core booking-correctness path (`lib/booking.ts`, `lib/availability.ts`, `lib/google.ts`, the Stripe webhook) is unusually rigorous: a real Postgres advisory lock + Serializable transaction + live calendar re-check + idempotent webhook claims + a partial unique index as a second line of defense, all with integration tests that exercise real concurrent Postgres transactions, not mocks. Typecheck, lint, and the unit suite all pass clean right now. The genuine problems are narrower and mostly clustered around: **alerting has a single point of failure (email) with no fallback**, **only one Google Calendar is checked for conflicts**, **rate limiting is trivially bypassable by anyone who isn't behind Vercel's edge**, **admin sessions can't be revoked**, and **reschedule doesn't exist** (cancel-and-rebook only). None of these are "double-booking will happen" bugs — they're "a failure will happen and you won't find out" or "abuse is easier than the code implies" bugs.

| `lib/availability.ts` | **KEEP** | Luxon-based, DST-safe, correct half-open-interval overlap math. One latent bug (guard-limit truncation, see F-1). |

| F-1 | `lib/availability.ts:72` (`while (day <= lastDay && guard++ < 400)`) | Low | Medium | The outer day-walk loop hard-caps at 400 iterations. `daysInAdvance` is clamped to max 365 in `lib/meeting-type-input.ts:87`, so this never bites today — but the guard and the input clamp aren't derived from each other, so a future change to either (e.g. someone raises `daysInAdvance` max, or someone copies this pattern elsewhere) can silently truncate availability with no error, no log, just fewer slots than configured. | Either derive the guard from `daysInAdvance`'s actual max (guard = max + 2) or assert the invariant in a comment/test tying them together. |

If the host keeps meetings on a second calendar (a shared team calendar, a "personal" calendar separate from "work"), BookKit will never see those as busy and will happily book over them — this is the literal double-booking scenario the whole locking architecture exists to prevent, just from a blind spot upstream of it, not a race. | F-3 | `lib/mailer.ts:26-33`, `lib/alerts.ts` (all four alert functions) | **High** | High | Every alert (`sendGoogleDisconnectedAlert`, `sendCalendarFailureAlert` — including the "AFTER PAYMENT" case — `sendConflictRefundAlert`, `sendWebhookSignatureAlert`) routes through `sendMail()`, which silently returns `false` and only logs a `warn` if `RESEND_API_KEY`/`RESEND_FROM` aren't set (`lib/mailer.ts:30-33`). `.env.example` and the README both describe email as "optional." | F-5 | `lib/http.ts:18-23` (`clientIp`) | **High** | High | `clientIp()` takes the first value of `X-Forwarded-For` verbatim with no trusted-proxy allowlist. ## Correctness deep-dive (the areas the user asked about explicitly)

- **Timezones / DST**: all wall-clock math in `lib/availability.ts` runs through Luxon in the host's IANA timezone; storage is always UTC (`prisma/schema.prisma:106` comment, enforced by convention throughout). DST transitions shift UTC instants automatically because Luxon computes from local wall-clock + zone, not fixed offsets. No bugs found.
- **Min notice / days-in-advance window**: computed once as `earliestMs`/`latestMs` bounds (`lib/availability.ts:47-55`) and applied uniformly to both the display path (`generateSlots`) and the write path (`isSlotOnGrid`, called inside the locked transaction at `lib/booking.ts:198`), so there's no drift between what's offered and what's accepted.
- **Buffers**: applied symmetrically as a padding window (`guardStart`/`guardEnd`) around both the candidate slot and the freebusy query, both at generation time and inside the lock at insert time. Verified with `tests/integration/concurrency.test.ts:140-157` (buffer test passes on real Postgres).
- **Daily limits**: counted per host-local calendar day via `dailyBookingCounts`, re-checked inside the lock (`dailyLimitReachedInTx`). Verified under real concurrency (`tests/integration/concurrency.test.ts:159-174`: 5 simultaneous bookers against `dailyLimit: 2` → exactly 2 succeed).
- **Existing-booking + Google-busy overlap**: both are queried and merged before every read (`getAvailability`) and re-checked live inside the lock before every write (`overlapsInTx` + `calendar().freeBusy(...)` at `lib/booking.ts:210-223`). The one real gap is **single-calendar-only** (F-2), not overlap math itself, which is correct half-open-interval logic throughout.
- **Race conditions / double booking**: `withHostLock` (`lib/booking.ts:74-103`) takes `pg_advisory_xact_lock(hashtext(hostId))` inside a `Serializable` transaction before any read or write, holding it across the live Google freebusy round-trip — this is the part that actually prevents the race (isolation level alone can't do it, since the calendar isn't inside the DB). Backed by a partial unique index (`Booking_live_slot_key`, migration `20260805180000_init/migration.sql:141-145`) as defense-in-depth for the exact-match case. `tests/integration/concurrency.test.ts` fires 5 real concurrent `createFreeBooking` calls against real Postgres and asserts exactly one wins — this is a genuine proof, not a mocked test.
- **Paid flow — hold vs. Stripe session lifetime**: `PAID_HOLD_MINUTES = 33` (`lib/booking.ts:50`) deliberately outlives `STRIPE_SESSION_MINUTES = 31` (`:51`), so payment can never land on a hold that already lapsed in our own DB. Stale unpaid holds are swept inside the same lock on every subsequent attempt (`sweepExpiredHoldsInTx`), which the CHANGELOG documents as a fix for a real prior bug (a hold that outlived its own expiry but was still counted "live" by the exact-match unique index, permanently burning a slot when the `checkout.session.expired` webhook never arrived). This fix is present in the current code.
- **Webhook idempotency**: both `finalizePaidBooking` and `finalizePaidIntent` claim the booking with a conditional `updateMany({ where: { ..., webhookProcessedAt: null } })` — only the first delivery of a duplicate Stripe webhook can win; later deliveries are logged and no-op'd (`lib/booking.ts:550-568`, `592-609`).
- **Crosstalk from the shared Stripe account**: both finalize functions look up the booking by an ID **BookKit itself generated and stored** (`stripeSessionId` / `stripePaymentIntentId`), never by trusting anything in the incoming webhook payload as an identity claim. An event for an unrelated site's checkout simply finds no matching row and is logged + ignored (`lib/booking.ts:544-547`, `586-590`, explicitly commented "Not one of ours — a shared Stripe account fires everything at everyone"). This is the correct pattern and it's implemented correctly.
- **Refund on failure**: if a payment lands but the slot was independently taken in the interim (`findPostPaymentConflict`), the booking is marked `FAILED_NEEDS_INTERVENTION`, an automatic Stripe refund is attempted, the booker gets an apology email, and the host gets a `[CRITICAL]` alert regardless of whether the refund itself succeeded (`handlePostPaymentConflict`, `lib/booking.ts:659-701`). If instead the payment succeeds and the *calendar write* fails (no slot conflict, just Google being unreachable), the money is deliberately **not** auto-refunded — the host is alerted to resolve it by hand, which is the right call (a calendar outage isn't proof the booking is invalid). Both paths are covered by `tests/integration/calendar-failure.test.ts` and `tests/integration/paid-booking.test.ts` against real assertions, not just "doesn't throw."
- **Google OAuth token refresh / failure modes**: tokens refresh proactively 60s before expiry (`lib/google.ts:88`) and persist the new access token + expiry to the DB. A refresh failure is classified (`isAuthFailure`) into either a terminal auth failure — which marks the host `googleAuthError`, sends `[URGENT]` alert, and makes `hostBookingBlocked()` return true so **new bookings are refused with a clear "email me" fallback rather than silently accepted and never reaching the calendar** — or a transient API error, which propagates up and causes the booking to fail closed (`BookingUnavailableError`) rather than proceed blind. This directly answers the user's stated worst fear ("silently lose a booking"): the code does not do that; it fails loudly and blocks new bookings instead. The one dependency this whole safety net has is F-3 (email must actually be configured for "alert" to mean anything beyond a log line).
- **Email sending failures**: `sendMail()` never throws; a failed/unconfigured send returns `false`, is logged, and is recorded on the booking row (`confirmationEmailError`) for admin visibility — it never blocks or rolls back the booking itself, which is correct (Google's own invite is the real confirmation channel per the README, and that's independent of Resend). The failure mode that matters is specifically the *alert* emails (F-3), not the booker-facing confirmation emails.
- **Cancellation token security**: `cancelToken` is a `cuid()` (`prisma/schema.prisma:133`), a reasonably high-entropy, non-sequential identifier — not cryptographically pure randomness like a UUID v4, but not guessable in practice either, especially combined with the cancel endpoint's rate limit (10/min/IP, `app/api/bookings/cancel/route.ts:11`, though see F-5 for how weak that limit actually is off Vercel). Double-cancel is handled gracefully (idempotent `alreadyCancelled` response, not an error). Only `CONFIRMED` bookings can be cancelled via this route.
- **Admin auth**: password compared via HMAC-then-timing-safe-equal (avoids both length leaks and non-constant-time comparison, `lib/auth.ts:23-28`) — this is meaningfully more careful than a naive `===` check. Every single admin API route independently calls `isAdmin()`/`assertAdmin()` at its own top (verified individually: `app/api/admin/bookings/[id]/route.ts:11`, `app/api/admin/meeting-types/route.ts:11`, `app/api/admin/meeting-types/[id]/route.ts:10,37`, `app/api/admin/settings/route.ts:13`) — none were found unprotected. Login itself is rate-limited (10 attempts/5min/IP, `app/api/admin/session/route.ts:16`), subject to the same F-5 caveat. Google OAuth connect/callback are also both admin-gated and use a proper random CSRF `state` cookie (`app/api/google/connect/route.ts:18-25`, verified server-side in the callback at `app/api/google/callback/route.ts:30-33`).
- **Embed widget**: `public/widget.js` validates `event.origin === ORIGIN` before trusting any `postMessage` from the iframe (`:194`), where `ORIGIN` is derived from the script's own `src` — correct. The resize handler matches the message to the specific iframe whose `contentWindow === event.source` before resizing, rather than trusting an ambient "resize the currently-open frame" assumption. The iOS `width:1px;min-width:100%` iframe-sizing hack (documented in code comments and confirmed as a real, previously-shipped fix per `CHANGELOG.md`) is correctly applied. No `innerHTML`/`eval` of untrusted data anywhere in the file.
- **Rate limiting**: present and applied consistently on every public money/spam-relevant POST route (`/api/bookings`, `/api/stripe/checkout`, `/api/stripe/intent`, `/api/bookings/cancel`, `/api/admin/session`) — nothing was found missing coverage. The implementation itself is honestly self-documented as advisory-only ("correctness never depends on it," `lib/rate-limit.ts:2-3`), which is true — no security *invariant* in this codebase depends on the rate limiter holding. Its real weakness is IP derivation (F-5), which undermines it as an actual abuse deterrent off Vercel.
- **Input validation**: `lib/validate.ts` + `lib/meeting-type-input.ts` reject malformed email/timezone/slug/time inputs server-side on every public route, independent of whatever the client-side form does; numeric fields (duration, days-in-advance, min-notice, buffer, daily limit, price) are all clamped to sane bounds server-side (`int()` helper, `lib/meeting-type-input.ts:27-31`), not just validated-or-rejected — meaning a malicious admin-panel request can't set `durationMinutes: 999999` even if it tried. Charge amount is always `meetingType.priceCents` read server-side, never client-supplied, in both the Checkout and PaymentIntent flows.

## Self-hosting friction (can an adopter get this running "in minutes"?)

The README's own claim is "~20 minutes," not "minutes" — and that number is honest. The path is: clone → `npm install` → Postgres (Supabase free tier or `docker compose up -d`) → `prisma migrate deploy` → Google Cloud Console OAuth client (external console, several clicks, one manual "add yourself as test user" step for personal Gmail accounts) → `npm run seed` → `/admin` login → connect Google → optionally Stripe CLI for local webhook testing → deploy to Vercel and repeat the OAuth redirect URI + reconnect step for the production domain. This is about as lean as a tool touching Google Calendar OAuth + Stripe can realistically be; the friction is inherent to those two integrations (both require console setup no CLI can automate), not to BookKit's own code. `lib/env.ts`'s `env()` trims whitespace defensively (the README even calls out the classic trailing-whitespace-in-hosted-secrets footgun explicitly) and every `requireEnv()` failure produces a clear, named error rather than a generic crash. No env var was found referenced in code but undocumented in `.env.example` (cross-checked `WEBHOOK_URL`/`WEBHOOK_SECRET`, `BOOKKIT_CALENDAR`, `HOST_TIMEZONE`, `DEMO_RESET_SECRET`, `NEXT_PUBLIC_APP_URL`, `ADMIN_EMAIL` all present). One real adoption risk: nothing stops a self-hoster from skipping Resend (it's genuinely optional and the app runs fine without it), which is exactly the condition that triggers F-3.

Recommend re-running `npm run db:up && npm test && npm run test:e2e` on a machine with Docker before going live, purely as a confirmation step — not because the suite looked hollow.
